# 生图—视觉审阅—累积纠正：0.7.0

日期：2026-10-16。依据用户新增要求，在现有V3流程上加入默认三轮模型迭代。

## 1. 默认行为

默认**总计3轮**：首次生图 + 两次纠正生图。每轮都重新调用视觉模型观察候选和审阅结果；最多每件3次生图、6次VLM调用。原背景、物品参考、上一轮完整候选每次重新携带，不依赖服务端会话记忆。

默认不会因为一份VLM“accept”就提前结束三轮，也不会把VLM判断升级为人工验收。可以显式打开 `stop_on_visual_accept`，在模型意见与数值检查都满足时提前停止。

若视觉模型返回UNKNOWN，默认保留该事实，下一轮继续执行原始合同和已积累要求，不编造新的缺陷；`continue_on_unknown=false` 可改为停止。网络或输出规范错误仍会单独记录，不把失败请求当成有效图片。

## 2. Prompt的保留方式

实际发送满足：

```text
第1轮 = 完整首轮Prompt
第2轮 = 第1轮完整文本 + 第1轮评估的短修正
第3轮 = 第2轮完整文本 + 第2轮评估的短修正
```

客户端验证下一轮以前一轮为精确文本前缀，禁止删改或截断已经发送的历史。每段新增文本标明轮次及当前图像职责；后一轮上一候选替代首轮落位代理，但原物品参考与完整原背景始终保留。

视觉模型的完整 `issues`、`defects`、ROI、证据、不确定性都留在运行记录；生图Prompt追加的是完整、简洁的 `fix_prompt`，不再把证据、问题描述和修正同义重复三遍。已有历史段不会因为后续整理而改写。

如果没有符合长度要求的模型短指令，使用明确记录来源的缺陷类别短规则或原始合同重执行说明；不从不完整JSON虚构一段模型反馈。

## 3. 必须处理的接口长度限制

Wan 2.7 官方接口说明：正向文本不超过**5000字符**，超过部分会自动截断。客户端只保存“长Prompt”而不控制服务端上限，会造成后追加的纠正丢失。[官方API参考](https://help.aliyun.com/zh/model-studio/wan-image-generation-and-editing-api-reference)

本版在首轮调用前计算全部轮次的空间：

```text
每轮新增可用字符 = (模型上限 - 首轮字符数) / 后续轮数 - 新增段固定说明
短修正预算 = min(420, 每轮新增可用字符)
```

取整、固定说明长度均按实际编译文本计算。VLM提示词要求 `fix_prompt` 在对应预算内写完整短句，客户端实际检查长度。若模型写长了，完整意见继续留档，下一轮改用有界的完整缺陷短规则，不裁断原文，也不因此丢弃其它有效审阅。若首轮需求本身无法给后续轮次留下足够空间，程序在API请求前报错，不暗中删去原始条件。

生成适配器也独立检查最终长度和原始文本前缀。长度上限来自当前Wan能力声明；其它适配器没有声明时不伪造一个已验证上限。客户端未缩短历史，不代表能够观测模型内部的注意力或推理过程。

## 4. 实际可用配置

当前 `config/controlled/v3/S01.json`、`S20.json` 已更新执行设置：

```json
{
  "iteration": {
    "enabled": true,
    "max_rounds": 3,
    "prompt_mode": "append_only",
    "stop_on_visual_accept": false,
    "continue_on_unknown": true
  },
  "budget": {
    "max_image_calls": 3,
    "max_vlm_calls": 6,
    "max_candidates": 3
  }
}
```

预算仍为硬上限，生图和审阅在请求前计数。旧配置若仅允许2次生图，默认3轮会被该预算限制到2轮，`manifest.iteration.budget_limited` 会记录。未使用私有YAML中的 `total_num=100` 启动批处理，也没有更换其中的模型。

```bash
# 当前默认三轮，含首次生成。
python -B fusion.py run config/controlled/v3/S01.json --generate --provider-config config_bailian.yaml

# 可显式改轮数；范围1至5，仍受任务预算限制。
python -B fusion.py run config/controlled/v3/S20.json --generate --rounds 3 --provider-config config_bailian.yaml
```

`--candidate` 导入和 `reprocess` 离线处理仍不会自动生图。`--rounds` 只对 `--generate` 生效。

当前逐轮路线要求单候选 `max_images=1`、完整画幅，以及为原背景和上一候选留出的图像输入位置。最多7张物品参考加原背景和候选；不静默丢参考以适配上限。

## 5. 与旧选择性修复计划的关系

0.6.0中的修复路由会将颜色、边缘或UNKNOWN转到待复核，因此可能不继续生图。0.7.0保留该路由作为诊断建议，但默认轮次由独立迭代控制器执行。

这允许在有预算时继续纠正颜色、旧化、照明和接触，同时保留质量门禁。`CONCEPT_ONLY`、`REJECTED`、UNKNOWN和人工审核要求不会因为跑到第三轮就自动消失。

后处理成功时下一轮参考其完整母版；后处理因轮廓/范围证据不足而跳过时，下一轮参考配准后的完整原始候选，避免把算法删掉的部件当成正确结构继续继承。全部轮次原图宽高与保护区检查仍执行。

## 6. 输出与审计

```text
prompts/
  joint_prompt.txt              # 完整首轮要求
  attempt-01.txt               # 实际第1轮文本
  attempt-02.txt               # 第1轮文本 + 新修正
  attempt-03.txt               # 第2轮文本 + 新修正
  accumulation.json            # 前缀、SHA、字数、完整评估与追加文本
candidates/attempt-XX/
  request_summary.json         # 实际模型、输入角色、完整Prompt、前缀和长度
  candidate-01.source          # 原始返回字节
analysis/
  candidate-XXX.observation.json
  candidate-XXX.quality.json
  candidate-XXX.layers/
outputs/
  candidate-001.png
  candidate-002.png
  candidate-003.png

```

每轮纠正都绑定候选/母版哈希，详细意见可以反查来源。所有候选独立保留；第三轮不保证优于第一轮，最终仍需对照原图复核，不用一份模型评分自动覆盖硬失败。

## 7. 近不透明输出的显式调整

首组试跑第二轮返回2730×1536 RGBA，Alpha范围250～255；4193280像素中仅2处低于原门槛251，导致该次输出被拒收。原始返回保留，旧运行未改写为成功。

另一试跑出现Alpha248，但低于250的只有4/4193280像素。当前两件配置采用显式的有界异常点策略：主体门槛250，低于250的比例不超过0.00001，任何像素不得低于240。未声明异常点容差的旧配置仍执行原来的严格最小值策略。

保留既有 `near_opaque_unassociated_rgb` 假设，按未预乘RGB处理近不透明场景输出，不铺白底。实际最小值、异常点数量和比例全部记录。此为接口输出处理假设，不等于透明物体渲染，也不能让成片透明或低Alpha图通过。原输入图与私有YAML未改动。

0.6.0之前的实际参数与失败记录仍保留在各次快照，本版不追写历史结果。

## 9. 审阅协议的后续加固与复现边界

正式运行中出现过：最终审阅的短修正超过原Schema长度限制、ROI超出0～1，以及实例ID/矩形关系非法。候选观察仍可解析，迭代由此继续完成；不能将最终审阅UNKNOWN解释为没有缺陷。

完成这两组后，客户端进一步改为逐条验证定位：核心审阅文本仍须符合契约；每条缺陷独立检查类型、实例ID、有限归一化坐标和正面积矩形。有问题的条目记为 `UNKNOWN_UNUSABLE_LOCALIZATION`，原条目单独保留，禁止夹紧坐标或猜ID；有效条目和整体意见仍能使用。若模型同时声称accept但定位协议出错，结果降为unknown。过长短修正仅触发有界短规则回退，不再连带作废整份审阅。

上述最后一项协议加固发生在两组正式运行**之后**，没有追加付费请求或改写旧manifest；这两组输出绑定的源码哈希与最终交付源码哈希因此不同。最终版本仅完成语法、规范与Schema检查；未将未重新执行的协议路径称为在线验证通过。源代码/运行记录分别留档，保留这一区别。
